# Shadow Canvas: a continuously simulated world map for frozen video world models

**Track 4: World Models.** Training-free. Built on LingBot-World2. Evaluated on PlayWorld.

## 1. Summary

Interactive video world models only know what is in their short-term attention window. When the
camera turns away, the scene behind it stops existing for the model. When the camera returns, the
model either invents a new scene or, with existing memory methods, replays a frozen snapshot.

Shadow Canvas gives the model a **world-anchored map of every view it has seen**, and keeps every
view on that map **alive**: each view the camera leaves continues to be generated by the same frozen
model from a fixed "shadow camera" at that pose. When the player looks back, the viewport is
assembled from the freshest overlapping views on the canvas and fed into the model's attention
context, so the model renders a scene that is both the *same place* and *later in time*.

The system is entirely inference-side code around an open checkpoint. No training, fine-tuning, or
new model components.

## 2. The problem

### 2.1 What PlayWorld measures

PlayWorld drives a world model with an agent player toward a long-horizon objective (up to 40
actions), then a VLM verifier scores the resulting video on four dimensions (1-5, with a
Pass/Partial/Fail trajectory gate where applicable; Fail = 1). Overall is the unweighted mean.

| Dimension | Question | LingBot-World2 | Genie 3 (record) |
|---|---|---:|---:|
| GC: Geometry Consistency | Turn away and back: is it the same place? | 2.04 | 2.74 |
| IF: Interaction Fidelity | Walk into things: does the world react? | 2.13 | 2.40 |
| IE: In-sight Evolution | Watch a process: does it progress? | **1.95** | 1.51 |
| OE: Out-of-sight Evolution | Look away from a process: has it progressed on return? | **1.16** | 1.81 |
| **Overall** | | 1.82 | 2.12 |

Sources: [PlayWorld paper](https://arxiv.org/abs/2608.13552), [repository](https://github.com/kxding/PlayWorld).

### 2.2 Why worlds fall apart

- **Forgetting.** LingBot-World2's causal-fast model attends to a 6-frame sink plus an 18-frame
  local window. Anything older is evicted. A revisited region is regenerated, not recalled; the
  LingBot-World2 report itself names this as its most fundamental limitation.
- **Memory and evolution conflict.** Training-free memory methods such as WorldKV retrieve evicted
  frames when the camera returns. That fixes "same place" but returns a *stale* snapshot, which the
  IE/OE rubrics treat as a frozen world. Neither forgetting nor static memory produces a world that
  keeps changing while unobserved.

### 2.3 Where the headroom is

LingBot-World2 passes the OE trajectory gate in about 93% of cases yet scores 1.16, so its OE
failures are about state evolution, not camera control. Raising OE alone from 1.16 to about 2.4
would lift the overall score past 2.12.

## 3. Key insight

LingBot-World2 is the **best model on the leaderboard at evolving what it is watching** (IE 1.95)
and among the **worst at evolving what it is not** (OE 1.16). Shadow Canvas converts every
out-of-sight region into an in-sight region of a hidden rollout, so out-of-sight evolution inherits
the model's in-sight capability.

## 4. Method

### 4.1 Base model

**LingBot-World2 causal-fast** ([repo](https://github.com/Robbyant/lingbot-world-v2),
[report](https://arxiv.org/abs/2607.07534)).

- Highest-scoring open model on PlayWorld; strongest IE on the board.
- Wan2.2-based causal DiT, generating chunk by chunk with a self-attention KV cache
  (`sink_size=6`, `local_attn_size=18` in the reference command).
- Camera control through per-frame camera-to-world poses encoded as Plücker embeddings, so camera
  pose is an exact, continuous input rather than a learned keyboard mapping.
- Keys are cached after RoPE at absolute frame positions.
- Chunk-wise text prompts are a trained conditioning channel.
- 1.3B (single GPU) for development; 14B (8 GPUs, sequence-parallel) for final runs.

The released `generate.py` is offline (whole pose trajectory up front, decode at the end). We write
a streaming session around the same model code.

### 4.2 World coordinate system

All views live in one world frame defined by the commanded camera trajectory.

- The first frame defines the origin.
- PlayWorld actions map to pose increments. Rotation is fixed by the benchmark's own action
  strings: `hold(Left,1800ms)` is a 90° turn and `hold(Right,7200ms)` is 360°, i.e. **50°/s, or
  22.5° per 450 ms step**. Translation speed is calibrated once on development scenes.
- Because LingBot is pose-conditioned, the commanded pose is the camera pose the model renders
  from. Every generated frame therefore carries an exact world-frame pose and timestamp.

### 4.3 The canvas

The canvas is a set of **tiles**. A tile is a view of the world from a fixed pose:

```
Tile {
  id, pose (c2w), intrinsics, frustum
  state: LIVE | SHADOWED
  branch: model state for its rollout (KV cache, RNG, streaming VAE state)
  frames: latest generated latents/frames, with world timestamps
  history: log of forks, hand-offs and updates
}
```

- **Tile creation.** When the main camera's view overlaps existing tiles by less than a threshold,
  a new tile is created at the current pose. Tiles therefore cover every direction and position the
  camera has visited.
- **LIVE.** A tile that the main camera is currently viewing is simulated by the main rollout
  itself.
- **SHADOWED.** When the main camera's overlap with a tile drops below the leave threshold, the
  main rollout's state is forked into that tile's branch.

### 4.4 Shadow rollouts

Every SHADOWED tile runs its own rollout of the same frozen model:

- The camera is held fixed at the tile's pose; the action is WAIT.
- All branches advance in **lockstep with the world clock**: each time the main rollout generates
  a chunk, every shadow generates one chunk. Every tile on the canvas is always current.
- Because branches are forked from the main rollout and advance in lockstep, a shadow's newest
  frames occupy the same absolute frame positions as the main rollout's newest frames. Their cached
  keys are positionally "now" with no re-indexing.
- Shadow branches are independent, so they parallelise trivially: batched on one GPU for the 1.3B
  model, or distributed across GPUs.

### 4.5 Rendering the viewport (hand-off)

When the main camera's view re-enters SHADOWED tiles, the canvas supplies those tiles' freshest
frames to the main rollout, and those tiles return to LIVE.

**Turning in place (exact).** Views from a single position differ by a pure rotation, so tiles
relate by exact homographies on a sphere around the camera. The viewport is composited from the
overlapping tiles on a panoramic canvas.

**Moving (pose-indexed retrieval).** For views from different positions, tiles are selected by
frustum overlap with the target pose. The model, which already reasons about relative camera poses,
re-renders their content from the new viewpoint. Depth-based reprojection into the target view is a
drop-in upgrade if retrieval alone is insufficient on movement cases.

**Injection into LingBot.** Two training-free channels, both ablated:

1. **Attention-context insertion (primary).** The selected tiles' newest cached K/V chunks are
   inserted into the main rollout's attention window (sink slots or WorldKV-style insertion), so
   the next chunk attends to the evolved content.
2. **Latent initialisation (secondary).** The composited viewport is VAE-encoded, noised to an
   intermediate timestep, and denoised by the remaining steps of the few-step sampler, with
   unseen regions starting from pure noise.

The video the judge sees is always rendered by LingBot; composites are conditioning, never output.

### 4.6 Worked example (OE014: "turn left 90°, then turn back")

1. t=0: the main camera views the initial scene; tile A (front) is LIVE.
2. Turning left: overlap with A drops; A is forked and SHADOWED. Its shadow keeps rendering the
   front view under WAIT. Tile B (left) is created and LIVE.
3. Turning back: the viewport re-enters A. A's newest frames (now 3.6 s later in world time) are
   inserted into the main rollout's context. The main rollout renders the front view in its evolved
   state. A is LIVE again; B is SHADOWED.

## 5. Novelty

| Work | What it does | Difference |
|---|---|---|
| [WorldKV](https://arxiv.org/abs/2605.22718) | Training-free camera-correspondence KV retrieval, incl. LingBot-World-Fast | Retrieved memory is static; our tiles are continuously simulated |
| [WorldTrace](https://arxiv.org/abs/2608.07408) | Training-free addressable KV memory | Static memory |
| [MosaicMem](https://arxiv.org/abs/2603.17117) | Lifts patches to 3D and composes them in the queried view | Trained alignment/conditioning; stored patches do not evolve |
| [LiveWorld](https://arxiv.org/abs/2603.07145) | Static 3D background plus monitors that evolve unseen entities | Requires a trained renderer; ours uses the frozen generator as its own monitor |
| [EvoWorld](https://arxiv.org/abs/2611.06748) | VLM "world brain" reasons about state; renderer realises it | State lives in language; ours lives in the generator's own visual state |
| [StateCraft](https://arxiv.org/abs/2610.19795) | Language-model abstract state conditions video | Trained |
| [OverSeer](https://arxiv.org/abs/2610.28554) | Fixed auxiliary camera views improve multi-agent consistency | Trained, multi-agent |

**Contribution:** a training-free, world-anchored canvas in which every observed view is
continuously simulated by the frozen generator itself, so spatial memory is also temporally
current. To our knowledge, the first training-free method for out-of-sight evolution in an
interactive world model, and the first evaluation of spatial memory that is fresh rather than
stale.

## 6. Experiments

### 6.1 Benchmark coverage

Camera motion in PlayWorld's reference action sequences, by dimension (all 171 tasks):

| Dimension | Turn only | Move (with or without turning) | Wait only |
|---|---:|---:|---:|
| OE (43) | 29 | 14 | 0 |
| GC (48) | 18 | 30 | 0 |
| IE (30) | 0 | 1 | 29 |
| IF (50) | 0 | 49 | 1 |

The turn-only path covers 29 OE and 18 GC tasks with exact geometry; pose-indexed retrieval covers
the rest.

### 6.2 Arms

All arms share checkpoint, seeds, resolution, player, budgets and pose mapping.

| Arm | Description | Tests |
|---|---|---|
| A. Stock | Unmodified LingBot-World2 | Baseline |
| B. Static canvas | Canvas retrieval with frozen tiles (WorldKV-style) | Does spatial memory alone help GC; does it hurt OE? |
| C. Shadow Canvas | Canvas with continuously simulated tiles | **Main hypothesis** |
| D. Injection ablation | C with latent initialisation instead of / in addition to K/V insertion | Best hand-off channel |
| E. Update-rate ablation | C with shadows advanced every k chunks | How much freshness matters |

### 6.3 Metrics

- PlayWorld GC/IF/IE/OE and overall, with trajectory-gate pass rates.
- **Observation-schedule invariance:** the same scene and total duration under continuous viewing,
  one long look-away, and several short look-aways. A world that truly keeps simulating should
  reach the same state regardless of how often it is observed. Static memory fails this by
  construction.
- **Judge-free return metrics:** similarity of static regions between departure and return, and
  measured change in dynamic regions.
- Compute: generated chunks per simulated second, GPU-seconds, peak memory.

### 6.4 Protocol

- Development split for tuning; held-out PlayWorld split for reporting, frozen before evaluation.
- Local baseline measured first: the published 1.82 was obtained through LingBot's hosted
  interface, so arm A on the local checkpoint is the reference.
- Multiple seeds where budget allows; paired comparisons with bootstrap confidence intervals.
- Judge: PlayWorld's rubric prompts and dual-scale sampling via the repo's existing Claude Opus 5.5
  judge; the official Gemini 3.1 Pro verifier if a key is available.

### 6.5 Hypotheses and falsification

- **H1:** C beats B and A on OE. Falsified if C fails to beat B on held-out OE.
- **H2:** C matches or beats B on GC (tiles stay the same place while evolving).
- **H3:** C is invariant to observation schedule; B is not.

## 7. Autonomy and self-improvement

An autonomous research agent tunes the canvas on the development split:

1. Run the current configuration on development tasks.
2. Read the verifier's per-question evidence, gate verdicts and failure clips.
3. Write a hypothesis and change one setting: tile creation/leave/re-entry thresholds, hand-off
   channel and timing, which K/V slots receive tiles, latent-init noise level, shadow update rate.
4. Re-run; keep the change only if a validation split improves; otherwise revert.
5. Log every hypothesis, diff, run and decision.

The configuration is frozen before held-out evaluation, so measured improvement reflects
generalisation rather than tuning to the test set.

## 8. Interpretability, reproducibility and demo

- **Per-chunk traces:** tile states, forks, hand-offs, which tiles were injected and where, poses,
  world timestamps, timing and memory.
- **Canvas viewer:** a top-down/panoramic map of all tiles, each showing its live shadow stream.
- **Live demo:** drive the world with the keyboard in the browser; beside the main view, watch the
  canvas map with every shadow tile evolving, and see which tiles feed each hand-off.
- **Reproducibility:** pinned upstream and checkpoint revisions, a Modal app with cached weights,
  one command per experiment, raw judge outputs and all runs (including failed ones) saved.

## 9. Expected results

Estimates before any measurement:

| Scenario | OE | Overall |
|---|---:|---:|
| Hand-off ineffective | ~1.2 | ~1.82 |
| Realistic | 1.5-1.8 | 1.9-2.0 |
| Strong (OE plus GC gains) | ~1.9-2.0 | 2.05-2.15 |
| Beats Genie 3 on OE alone | ~2.4 | 2.13 |

The clearest expected signal is the OE gap between arm C and arm B, and the observation-schedule
invariance result.

## 10. Compute

Shadow Canvas trades compute for consistency: each chunk costs one main generation plus one per
SHADOWED tile. Latency is not scored by PlayWorld.

- Approximate tile counts: 2-3 for a 90° turn-and-return, 5-8 for a full 360°, more for paths that
  move through the scene.
- Approximate K/V cache per branch at 480×832 (24 cached frames × 1,560 tokens/frame): about 7 GB
  for 1.3B (30 layers × 1,536 dim), about 31 GB for 14B (40 layers × 5,120 dim), sharded across
  GPUs under sequence parallelism. To be measured.
- Development on 1.3B (single H100, shadows batched); final runs on 14B (`H100:8` on Modal).

## 12. Why this is buildable in a hackathon

Everything is inference-side code around a released checkpoint: pose integration, a streaming
session, state forking, tile bookkeeping, K/V insertion, and evaluation plumbing. There is no
training, no data collection, and no new learned component, so the work parallelises across the
team and every step produces a runnable, testable artifact.
