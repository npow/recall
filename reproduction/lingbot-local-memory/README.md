# Local Thor memory feasibility and isolated prototypes

The initial assessment was CPU-only. A subsequently authorized, supervised two-chunk local stage now completes; its measurements are below. The machine has131.86GB physical RAM visible to Linux (122.8GiB), with108.74GB available at the initial snapshot. Thor shares this RAM with CPU processes; GPU allocations are not an independent memory pool.

The existing BF16 CPU archive occupies19.766GB. Symmetric int8 codes with one FP32 scale per token/head vector reduce it to10.192GB, including scales:48.44% less storage. A CPU probe on BF16 features gives relative reconstruction error0.00647. This is lossy feature compression, not a validated video-quality improvement.

An isolated `Int8ArchiveMemory` subclass stores only compressed CPU features and dequantizes selected frames on the GPU before the existing BF16 read cache and RoPE operation. Native persistent KV tensors and model parameters stay unquantized. Six CPU tests cover error bounds, storage accounting, nonfinite rejection, encoder disposal and a tiny real upstream attention block. In that block native KV tensors and pre-retrieval outputs remain exact; retrieved attention output changes by less than3% in the tested case. Longer generated-video quality remains untested.

The separate one-shot text-encoder proxy computes the original context, then replaces T5 parameters with meta tensors immediately after encoding, before native VAE/KV allocation. It preserves the frozen rollout's later `.cpu()` call as a no-op and rejects another encode. A CPU test checks exact encoded output and removal of the parameter payload. It is deliberately unsuitable for persistent multi-request workers.

Using the existing72.76GB GPU peak as a conservative proxy,10.19GB compressed archive,5GB process/transient allowance and6GB allocator allowance gives93.95GB for the application. That leaves14.79GB available at the snapshot, below the required16GiB (17.18GB) system reserve. **The conservative full-memory budget does not pass.** T5 disposal should improve the actual stage peak, but that must be measured on Thor rather than assumed from a discrete GPU.

The guarded two-chunk stage used no archive, native unquantized KV, and one-shot T5 disposal. It produced29 finite frames and passed both native-camera audits. Runtime was262.16seconds: pipeline loading took177.55seconds; the second generated second took37.67seconds. The DiT payload is37.089GB, entirely BF16. T5 disposal released11.362GB before native KV allocation. Peak process RSS was61.943GB during loading; exact CUDA peak allocation was68.669GB and sampled peak reservation72.664GB. Minimum sampled MemAvailable was28.734GB, above the16GiB watchdog reserve; no reserve abort occurred. CPU RSS and CUDA values describe different shared-memory accounting views and should not be blindly summed.

The first attempt failed because a global FlashAttention restriction also covered VAE attention with384-dimensional heads, unsupported by that kernel. Its complete logs and memory samples are retained in [failed-global-flash](failed-global-flash/). The successful retry restricts FlashAttention only for DiT self/cross attention and keeps native VAE backend selection. The first version of the VAE shape logger only recognized512-dimensional heads; it collected no shapes in the successful run. Its future guard now includes all heads above256 and all FP32 attention. The completed measurement is retained unchanged.

The full-memory pair remains unlaunched: adding10.19GB of private int8 archive plus up to4.94GB of GPU reads would exceed a conservative16GiB-reserve projection from the observed minimum. The next isolated prototype is lossless file-backed BF16 history, with flushed/evicted mapped pages, to avoid a quantization confound and a private20GB archive. Its CPU bit-exact and native-attention tests must pass before any complete13-chunk local baseline and memory pair.
